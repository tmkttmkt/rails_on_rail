# Design: AI連携用APIのVite開発サーバー組み込み

## 目的

「AIが人間のゲーム画面に直接干渉し、ペアプログラミングのようにペアプレイを行える環境」を構築する。
Rails on RailのシミュレーションロジックはUIから独立しているため、ブラウザ外のAI（またはスクリプト）が `MapCommand` を生成して流し込むだけでゲームを操作できる。これを実現するための最も軽量な通信経路として、Vite開発サーバーを拡張したAPIを定義する。

## API仕様（Phase -1 現在）

### 1. 状態同期 API (`/api/state`)

AIが現在のゲーム状況を把握するためのエンドポイント。

- **POST /api/state**
  - **送信元**: ブラウザ (毎秒実行)
  - **Body**: 現在の `MapState` のJSON文字列
  - **処理**: サーバーがメモリ変数にJSONを上書き保存する。
- **GET /api/state**
  - **送信元**: AI / 外部スクリプト
  - **レスポンス**: メモリに保存されている `MapState` のJSON

### 2. サーバーサイド・セーブ管理 API (`/api/server-saves`)

ブラウザのLocalStorageに依存せず、AIや人間が検証用マップなどを共有・永続化できるよう、Viteサーバーを介してローカルPC上の実ファイル（`saves/*.json` 等）としてセーブデータを読み書きするエンドポイント。

- **GET /api/server-saves**
  - **送信元**: AI / ブラウザ
  - **レスポンス**: サーバーの指定ディレクトリ内に存在するセーブデータJSONファイルの一覧（メタデータ）を返却する。
- **POST /api/server-saves**
  - **送信元**: AI / ブラウザ
  - **Body**: 保存したい `SaveFile` 形式のJSON（ファイル名などを指定）
  - **処理**: Node.jsの `fs` を利用して、プロジェクト内の `saves/` などのディレクトリにJSONファイルとして物理保存する。
- **GET /api/server-saves/:filename**
  - **送信元**: AI / ブラウザ
  - **処理**: 指定されたJSONファイルを読み込み、`/api/load` のような形でブラウザの状態に復元（注入）する。

### 3. コマンドキュー API (`/api/commands`)

AIがゲームに対して操作指示を出すためのエンドポイント。

- **POST /api/commands**
  - **送信元**: AI / 外部スクリプト
  - **Body**: `MapCommand` 型のオブジェクト、またはその配列
  - **処理**: サーバーが受け取ったコマンドをメモリ上のキューに追加する。
- **GET /api/commands**
  - **送信元**: ブラウザ (毎秒実行)
  - **レスポンス**: キューに溜まっているコマンド配列のJSON
  - **処理**: ブラウザ側へ返却後、キューを空にする。

## アーキテクチャ上の重要な判断

### A. URLをコマンドごとに分割しない理由（Unified Endpointの採用）

RESTfulなAPI設計では `/api/track/create` や `/api/station/delete` のようにURLを分割するのが一般的だが、本システムでは意図的に単一の `/api/commands` を採用している。

1. **トランザクション（一括操作）の保証**: AIが「線路を引いて駅を置く」という複数のコマンドを配列にして1回のPOSTで送信できるため、描画が途切れず安全に状態を遷移させられる。
2. **メイン開発への非干渉（メンテナンスフリー）**: ゲーム本体（Codex担当部分）で新しい `MapCommand` が追加されたり仕様変更されても、ViteのAPIサーバー側のルーティングを修正する必要が一切ない。

### B. 将来のState細分化（Delta Sync）の展望

現在は `/api/state` でマップ全体のJSONを毎秒送信しているが、マップが拡大するとパフォーマンスの問題となる。
将来Phaseが進んだ段階で、`/api/state/tracks` のようにリソースを細分化したり、変更差分だけを同期する **Delta Sync** の仕組みへと拡張する。

## AI側（操作側）で必要になる機能拡張（Phase -1 スコープ）

AIがこのAPIを活用して自律的な操作やサポートを行うためには、AI自身のスクリプト（ラッパー）として以下の機能を整備していく必要がある。

### 1. 軌道・空間操作関数
- **座標の検索**: `MapState` から未接続の端点座標や、建設可能な空白領域を逆算する。
- **線路パス生成**: 2点間の直線・曲線パス（`points: Point[]`）や、スナップ接続用ベクトルを自動算出する。
- **駅範囲の計算**: 指定した距離・位置に基づき、駅の正確な `startPosition` と `endPosition` を算出する。

### 2. セーブデータ（JSON）の入出力・管理機能
AIが過去の検証状態を復元したり、作成したマップをアセットとして保存するための機能群。
- **セーブデータの取り出し**: `GET /api/state` で取得したJSONに管理メタデータ（`SaveMetadata`）を付与し、セーブデータファイルとしてディスクに書き出す。
- **セーブデータの読み込み（注入）**: 任意のセーブデータJSONを読み込み、API経由でブラウザへ注入する（`/api/load` で実装済み）。
