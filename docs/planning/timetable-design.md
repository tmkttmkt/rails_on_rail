# 長期課題: ダイヤの設計

複数Phaseにまたがる未解決の設計課題。実装方針が固まるたびにこの文書を更新し、採用案と理由を記録する。

## 課題の核心

**詳細さ** と **操作の楽さ** のトレードオフ。

ダイヤを詳細に扱うほど単線での交換・追い越し・接続の設計が面白くなる。
しかし路線数・列車数が増えると管理が破綻し、ゲームがダイヤ作業だけになる。

---

## ダイヤが影響する要素

| 要素 | 内容 |
|---|---|
| 輸送量 | 本数 × 定員 = 時間あたり輸送能力 |
| 所要時間 | 停車・交換待ちを含めた実際の移動時間 |
| 接続 | 乗り換え待ち時間が需要に影響 |
| 単線制約 | すれ違い可能な駅でしか列車が行き違えない |
| 遅延 | 1本の遅れが後続列車に波及する |
| 車両運用 | 折り返し時間・車両の滞在場所 |

---

## 設計の選択肢

### A. 本数指定（Frequency-based）

プレイヤーは「1時間あたり何本」だけ設定する。列車位置はシステムが自動で割り振る。

- **利点**: 最も操作が楽。路線数が増えても管理しやすい
- **欠点**: 単線のすれ違い問題を表現できない。接続の設計ができない
- **向いているPhase**: Phase 2の導入段階

### B. パターンダイヤ（Pattern timetable）

「○時間ごとにこのパターンで走る」という繰り返し単位をプレイヤーが設計する。

```
例: 毎時パターン（60分サイクル）
  A発 :00  → B着 :20  → C着 :40（折り返し）
  C発 :00  → B着 :20  → A着 :40（折り返し）
```

- **利点**: 本数指定より詳細。現実の地方路線ダイヤに近い。操作量は管理可能
- **欠点**: 不規則なダイヤ（特急・臨時）を表現しにくい
- **向いているPhase**: Phase 2–3

### C. 列車スジ（Train graph / 列車ダイヤ）

縦軸=駅・横軸=時刻のグラフ上で、各列車の運行を1本ずつ設計する。日本の鉄道で実際に使われる手法。

- **利点**: 最もリアル。すれ違い・追い越し・接続を完全に制御できる
- **欠点**: 路線が増えると管理が爆発する。プレイヤーの習熟コストが高い
- **向いているPhase**: Phase 3以降のオプション機能として検討

### D. シミュレーション自律型

明示的なダイヤなし。列車が設定ルールに従って走り、競合はシステムが解決する。

- **利点**: プレイヤーの作業量が最小
- **欠点**: 結果が予測しにくい。非現実的な動きが起きやすい
- **向いているPhase**: Phase 0（暫定実装）として使い、後で廃止

---

## 単線すれ違いの扱い

複線は上下線が独立するため競合が生じない。
単線では列車同士が同じ線路を使うため、すれ違い可能な駅（交換駅）で片方が待たなければならない。

これをどう扱うか：

| 方法 | 内容 |
|---|---|
| 無視 | 単線でも複線と同じ扱い。リアリティなし |
| 容量制限 | 単線は複線の半分程度の本数しか設定できない制約を課す |
| 交換計算 | 交換駅の位置と本数から自動で待ち時間を計算 |
| ダイヤ上で明示 | プレイヤーがどの駅で交換するかを指定 |

Phase 2では「容量制限」から始め、Phase 3で「交換計算」への移行を検討するのが現実的。

---

## 接続（乗り換え）の扱い

幹線と支線の接続時刻が合わないと実質的な所要時間が伸び、需要が落ちる。

最小限の再現案：
- 接続駅での「接続時刻のズレ」を計算し、実効所要時間に加算する
- プレイヤーはパターンダイヤの開始時刻をずらすことで接続を改善できる

---

## 未解決事項

- 単線すれ違いをゲームの「パズル」として面白く扱えるか、それとも自動化すべきか
- ピーク時間帯の増発をどう扱うか（パターンダイヤで表現可能か）
- 遅延のシミュレーションをどの程度リアルにするか
- 車両の折り返し・夜間滞泊をゲームとして扱うか

---

## Phase別の導入方針（案）

| Phase | ダイヤの扱い |
|---|---|
| Phase 0 | ダイヤなし。列車が経路を走るだけ |
| Phase 1 | 路線ごとに「1日の本数」だけ設定する |
| Phase 2 | パターンダイヤ導入。単線は容量制限で表現 |
| Phase 3 | 交換駅の計算、接続待ち時間を導入 |
| Phase 4以降 | 列車スジの採用要否を改めて判断する |
