# 長期課題: 需要の設計

複数Phaseにまたがる未解決の設計課題。実装方針が固まるたびにこの文書を更新し、採用案と理由を記録する。

## 課題の核心

**リアリティ** と **計算量・管理可能性** のトレードオフ。

需要をリアルに再現するほど計算が重くなり、データ量が増え、プレイヤーが把握しきれなくなる。
単純化するほど「作れば稼げる」になり、廃線・縮小の判断が生まれなくなる。

---

## 需要を決める要因

| 要因 | 内容 | 変化の速さ |
|---|---|---|
| 人口 | 拠点の居住者数 | 十年単位でジワジワ |
| 産業 | 鉱山・工場・農産地・商業 | 産業サイクルで数十年 |
| 土地利用 | 住宅地・農地・山林 | 鉄道投資で変化（誘発需要） |
| 競合交通 | 道路整備・バス・航空 | モータリゼーションで急変 |
| 運賃・速度 | 鉄道自体の利便性 | プレイヤーが直接制御 |
| 時間帯 | 朝夕ピーク・昼間閑散 | 毎日繰り返す |

---

## 設計の選択肢

### A. 重力モデル（Gravity model）

駅A–B間の需要 ∝ 人口(A) × 人口(B) ÷ 距離(A,B)²

- **利点**: 計算が単純、人口配置から自然にパターンが生まれる
- **欠点**: 競合交通・土地利用を自然に組み込みにくい
- **計算量**: O(n²)。駅数が増えると重い

### B. ゾーン集計

複数の駅をゾーンにまとめ、ゾーン間で需要を計算する。

- **利点**: 駅数が増えても計算量を抑えられる
- **欠点**: 駅単位の精度が落ちる。ゾーン境界の設計が難しい
- **計算量**: O(z²)（z = ゾーン数）

### C. 路線需要曲線

路線ごとに「所要時間・本数・運賃に対する需要関数」を持つ。

- **利点**: 実装が最も単純。チューニングしやすい
- **欠点**: ネットワーク効果（乗り換えによる遠距離移動）を表現できない
- **計算量**: O(路線数)

### D. エージェントベース

仮想的な住民個々が移動手段を選択するシミュレーション。

- **利点**: 最もリアル。誘発需要・モード選択が自然に生まれる
- **欠点**: 計算量が大きく、デバッグが難しい
- **計算量**: O(エージェント数 × 探索コスト)

## 誘発需要の扱い

「鉄道を引いたから人が来た・町が発展した」という効果。これがないと先行投資の意味が薄れる。

最小限の再現案:
- 駅設置後、一定期間かけてその地域の人口・産業が緩やかに増加する
- 増加率は路線の本数・速度・接続先に依存する
- 増加には上限を設け、過疎地での過剰期待を防ぐ

---

## 計算タイミングの選択肢

| タイミング | 内容 | 負荷 |
|---|---|---|
| リアルタイム（毎フレーム） | 常に最新需要を参照 | 高い |
| ターン単位（年・季節） | ターン終了時に一括更新 | 低い |
| イベント駆動 | 路線変更・人口変化時のみ再計算 | 変動 |

ターン制のゲームであればターン単位が最も扱いやすい。

---

## 未解決事項

- 何駅・何路線の規模まで扱うか（スケール上限）
- 時間帯（朝ピーク）をゲームとして扱うか、それとも「1日平均需要」に圧縮するか
- 誘発需要の強度をどの程度リアルに設定するか
- 需要データをプレイヤーにどう見せるか（路線図上のヒートマップ、数値表など）

---

## Phase別の導入方針（案）

| Phase | 需要の扱い |
|---|---|
| Phase 0 | 需要なし。列車が動くことの確認のみ |
| Phase 1 | 駅間の固定需要。単純な路線需要曲線で導入 |
| Phase 2 | 本数・速度に応じた需要変化。ピーク係数を追加 |
| Phase 3–4 | ゾーン集計または重力モデルへ移行を検討 |
| Phase 5–6 | 人口変化・競合交通・誘発需要を動かす |
