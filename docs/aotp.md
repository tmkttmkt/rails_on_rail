# AOTP: エージェント指向テキストプログラミング

## 背景

かつて、機械は曖昧さを解釈できなかった。人間の意図をそのまま渡しても動かない。だからプログラミング言語が生まれた。プログラミング言語とは、人間と機械の中間に置かれた変換層だった。

今や、機械はテキストを解釈し、実行できる。自然言語の指示を読み、コードを書き、判断し、引き継ぐことができる。

この変化は「何がプログラミングか」の定義を変える。エージェントが読む入口ファイル（`CLAUDE.md` / `AGENTS.md`）を書くこと、SKILLを定義すること、ドキュメントの構造を整えてリンクで繋ぐことは、もうプログラミングと呼んで過言ではない。

今後、AIの投入量は増え、コストは下がり、モデルの種類はさらに多様化する。汎用・コーディング特化・レビュー特化・調査特化など、役割の異なるエージェントを組み合わせて動かすことが当たり前になる。すでにその多様化は始まっている。Codexは自律的で純粋なプログラミングが得意でクラウドで長時間タスクを実行したりする、Claude Codeは人間以上の読解力を示しターミナルで対話的にコードを書いたりする、Copilotはcodexやclaudecodeの旧世代軽量モデルを廉価に提供する。得意領域も、動く場所も、人間との関わり方も、AI提供の形もそれぞれ異なる。さらに加速するだろう。

これは、AIの投入量がそのまま開発スピードに変換されることを意味する。ただし、タスクが分解され、役割が定義され、状態が共有されていれば、という条件のもとで。分解されていないタスクにエージェントを積み上げても、文脈が重複し、成果が衝突し、整合に追われるだけになる。こ

数を力にするには、構造が先に要る。AOTPはその構造をテキスト文書として設計するための思想である。

## 定義

AOTP（Agent-Oriented Text Programming / エージェント指向テキストプログラミング）は、人間とAIをどちらもエージェントとして扱い、Markdownによって状態・意図・制約・判断を外部化する開発思想である。

目的は、各エージェントが少ない資源で現状を把握し、想定通りで安定した成果を出力できるようにすること。

ここでいう少ない資源とは、次の3つを指す。

- コンテキスト
- 処理時間
- 必要最小限のみの許可や会話

## 原則

AOTPの原則は **上部原則（4つ）** と、各上部原則の下に属する **下部原則** で構成される。

| 上部原則 | 下部原則 |
|---|---|
| **MD公理** | — |
| **エージェント化** | 権限の明示化、非同期協調 |
| **外部化** | 一文書一責務、冪等性、文書とコードの同時更新、検証可能性 |
| **省資源化** | 連鎖リンク、段階的詳細化 |

### MD公理

世界の状態、意図、制約、判断、計画、履歴、成果物の説明はMarkdownで記述できるし、記述すべきである。

Markdownは単なる説明文ではない。人間とAIエージェントが同じ文脈を読み、判断し、次の出力を作るための共通状態表現である。

Markdownは役割によって次の3種類に分類する。

| `md_class` | MD分類 | 役割 | 扱い |
|---|---|---|---|
| `operation` | **運用MD** | 作業方法、規約、制約、判断基準を定義する | 存在する内容を現在有効な運用として扱う。問題があれば直接修正し、不要なら削除する。過去状態はGit履歴に残す |
| `history` | **履歴MD** | 提案、調査、設計、判断、タスク、実装差分を記録する | 確定後は原則変更せず、訂正や置換は後続文書とのリンクで表現する |
| `status` | **状況MD** | 現在の機能、構成、仕様、タスク一覧を表す | 実装や作業状態と同時に更新し、常に現在の状態と一致させる |

すべてのAOTP管理対象Markdownは、ファイル先頭のYAML frontmatterに自身の分類を明記する。分類名は表示上の日本語に依存させず、機械処理しやすい固定値 `operation` / `history` / `status` を使う。

```markdown
---
md_class: operation
---

# 文書タイトル
```

運用MDは単なる手順の説明ではない。エージェントが読み、判断し、コマンド実行、ファイル変更、検証、停止、引き継ぎなどの行動を決定するための、自然言語で書かれた事実上のスクリプトである。入口文書、workflow、規約、policy、SKILL、Project Profileは、エージェントに対する制御フローと実行条件を構成する。したがって、運用MDの曖昧さ、矛盾、古いパスやコマンドは、プログラムの不具合と同じように扱い、見つけた時点で現在の運用を修正する。

分類は文書の読み方と更新方法を決める。運用MDを履歴として残したり、履歴MDを現在仕様へ合わせて書き換えたり、状況MDを古い状態のまま凍結したりしてはならない。未採用の運用案は会話の中だけで検討し、採用された時点で運用MDへ反映する。

taskは、目的、完了条件、実装結果、検証証拠、途中のcheckpointを後から復元するための履歴MDとして扱う。進行中taskを含む現在の作業状態は、taskメタデータから生成または更新するタスク一覧を状況MDとして表現する。task完了後は凍結し、問題が見つかった場合は後継taskを作成して接続する。

### エージェント化

人間とAIを、性能・権限・責任・速度・記憶・得意領域が異なるだけの思考エージェントとして扱う。

どちらもMarkdownを読み、文脈を解釈し、判断し、次のMarkdownまたは成果物を出力する主体である。AOTPでは、人間だけに分かる状態やAIだけに閉じた状態を減らし、同じテキスト基盤上で協調できるようにする。

#### 権限の明示化

各エージェントが何をできて何をできないかをテキストで定義する。

どのエージェントが何を読んでよいか・何を変更してよいか・何を承認できるかを明示する。エージェントは自分の役割に必要なファイルだけを読む。関係のないファイルを読むことはコンテキストを消費し、判断を曇らせる。権限と読む範囲を絞ることは省資源化でもある。

#### 非同期協調

エージェントは同時に動かなくても協調できる。

Markdownが橋渡しをするため、エージェントAが終わってからエージェントBが始まる形でも、並列で動く形でも、Markdownの状態さえ正確であれば引き継ぎが成立する。リアルタイムの同期を前提にしない設計が、並列・クラウド・長期プロジェクトを可能にする。

### 外部化

暗黙知、会話中の判断、作業状態、未解決事項をMarkdownに外部化する。

エージェントの記憶やチャット履歴だけに依存しない。次に読むエージェントが、必要な文脈をファイルから復元できる状態にする。

#### 一文書一責務

1つのファイルは1つの関心事だけを持つ。

提案書に設計の詳細を書かない。設計書に実装結果を混ぜない。関心事が混在すると、次のエージェントはどこまでが確定情報でどこからが参考情報か判断できなくなる。役割が明確なファイルだけが、連鎖の正確なノードになれる。

#### 冪等性

どのエージェントがいつ読んでも、同じ理解が得られる文書を書く。

文書の内容が「この会話を知っている前提」「このコミット以降の変更を見た前提」に依存していてはならない。文書単体で状態が完結していること。文脈を失ったエージェントが文書だけを読んで復帰できることが冪等性の基準である。

#### 文書とコードの同時更新

コードが変わったら、文書も同じコミットで変える。

「後でドキュメントを直す」は機能しない。次のエージェントはコードと文書の両方を読んで判断する。どちらかだけが正しい状態は、誤った前提で作業するエージェントを生む。

#### 検証可能性

文書に書いた主張は、リンク・コード・テスト結果で裏付けられる状態にする。

「〜している」と書いたなら、確認できるファイルやコードへのリンクがあるか、テストが存在するかのどちらかが必要である。裏付けのない主張は劣化し、やがて誤情報になる。

### 省資源化

Markdownは長ければよいわけではない。少ないコンテキスト、処理時間、許可、会話で現状把握と成果出力ができるように構造化する。

目的、現状、判断、未解決事項、関連リンクを分けて書く。読む順番や対象ファイルも明示する。

#### 連鎖リンク

省資源化の中核をなす設計パターンが連鎖リンクである。

エージェントがすべての文書を一度に読む必要はない。入口文書（`CLAUDE.md`）が次の文書（`workflow.md`）を指し、その文書が該当する提案書を指し、提案書が設計書を指す。エージェントはチェーンを辿ることで、今の作業に必要な文脈だけを順番に取得できる。

```
CLAUDE.md → Project Profile → task-index.md → tasks/xxx.md → 関連文書 → 実装
```

このリンクの連鎖は制御フローである。どのファイルが何を指すかを設計することは、エージェントの注意をどこに向けるかをプログラムすることと同義である。

連鎖リンクが機能するためには：
- 各文書が「次に読むべきもの」を明示すること
- リンク先が存在し、内容が現在の状態と一致していること
- 一つの文書が複数の関心事を混在させないこと（読み手が途中で迷子になる）

会話でやり取りした判断や未解決事項は、チェーンのどこかの文書に落とさなければ次のエージェントには届かない。「口頭で伝えた」は連鎖から外れた情報であり、存在しないに等しい。

#### 段階的詳細化

上位文書は概要とリンクだけを持ち、詳細は下位文書に委ねる。

`CLAUDE.md` → Project Profile → Task一覧 → Task → 関連するDesign・Research・Decision・状況MDの順に詳細になる。入口文書が詳細を抱え込むと、エージェントは全体を読まなければ作業を始められなくなる。概要から詳細へ一方向に辿れる構造が、連鎖リンクの前提である。

## 運用手順

### 1. 起動する

作業を始めるエージェントは、入口文書から連鎖を辿り、ブランチとworktreeを作って作業領域を確立する。

**読む順番**

入口文書から始め、指示されたファイルを順に読む。

- `AGENTS.md` / `CLAUDE.md` — プロジェクト全体の制約と方針
- `docs/workflow.md` — 役割・フェーズ・ブランチ運用
- `docs/conventions.md` — コーディング規約
- 担当Taskと、その`relations`が示すDesign・Research・Decision・状況MD

日本語を含む可能性があるファイルはUTF-8として読む。文字化けした出力を根拠に判断しない。

**ブランチとworktreeの作成**

```bash
# ブランチ名: agent/<tool>-<model>-<n>/<slug>
git worktree add ../DenUni-<id>-<slug> -b agent/<id>/<slug>
```

worktreeを作らずにブランチだけ切ると、シェルをまたいでブランチが保持されず別ブランチにコミットが入るリスクがある。人間から明示的に「worktreeは不要」と指示された場合のみ省略してよい。

### 2. 状態を分類する

情報を役割ごとに分ける。

- `docs/tasks/` — 今回何を完了させ、何を検証したか
- `docs/proposals/` — 採否や選択肢を検討した履歴
- `docs/research/` — 調査で分かった事実
- `docs/designs/` — どう作るか
- `docs/features/` — 実装済み機能の仕様
- `docs/impl-note/` — 実装時の判断、設計との差分、将来の注意点
- `.agents/skills/` / `.claude/skills/` — エージェントの作業手順（SKILL）

分類されていない情報は、次のエージェントが読むときに余計な探索を生む。

### 3. 文書の鮮度を確認する

読んだ文書が現在の実態と一致しているか確認する。

- ファイルパス・関数名・テーブル名が実際のコードと一致するか
- リンク先が存在するか
- type固有のstatusとTaskの完了条件が実態に合っているか
- 最終更新日が古すぎないか

不一致を見つけたら、作業の前に修正するか、未解決事項として記録する。古い文書を正しい前提で読み進めると、誤った実装を生む。

### 4. SKILLを活用する

定型的な作業手順はSKILLとして定義されていることがある。作業前に該当するSKILLが存在するか確認する。

- テスト実行 → `/test-local`（ローカル）/ `/test-remote`（リモート確認）
- コミット → `/commit`
- コードレビュー → `/code-review`（Claude Code組み込み）

SKILLがない作業で手順が複雑なら、作業後にSKILLとして残すことを検討する。SKILLはエージェントの連鎖リンクに組み込める再利用可能な手順書である。

### 5. Markdownに外部化する

会話や作業中に決まったことは、必要に応じてMarkdownへ移す。

外部化するものの例:

- 目的・背景・制約
- 判断理由
- 未解決事項
- 実装手順
- 検証結果
- 次の作業者への注意

「分かっているはず」にしない。Markdownに書かれていない状態は、次のエージェントにとって存在しない状態に近い。

### 6. Markdownを根拠に実行する

実装、調査、設計、テスト、コミットは、Markdownに書かれた状態・制約・手順を根拠に進める。

コードだけが変わり、文書上の状態が古いままだと、次のエージェントは誤った前提で作業する。コードと文書は同じコミットで更新する。

### 7. 結果・差分を検証し、ずれを記録する

作業後は成果物だけでなく差分も確認する。

確認するものの例:

- 変更ファイルとstaged diff
- リンク先の存在
- 文字コード
- テスト結果
- センシティブファイルの混入（`.env` / `*.sqlite3` / `.denuni_session.json`）
- 未解決事項の残り

確認できなかったことも未実行として残す。

設計書や提案書に書いた内容と実際の実装が異なる場合は、`docs/impl-note/` に補足メモを作成する。ずれを隠すと次のエージェントが誤った設計を前提に作業する。

### 8. 判断を残して引き継ぐ

次の人間・AIが少ない資源で復帰できるように、判断と状態を残す。

特に次を明示する:

- 何を完了したか
- 何をまだ決めていないか
- どの文書を読めばよいか
- どの制約を守るべきか
- なぜその判断にしたか

### 9. 並列エージェントを調整する

複数のエージェントが同時に動く場合、作業領域を分離して衝突を防ぐ。

**ローカル並列（Claude Code / Codex など）**

エージェントごとにworktreeを分け、別々のブランチで作業する。同じファイルを同時に編集しない。マージはdevelopに順番に行い、コンフリクトは後からマージする側が解消する。

```bash
# エージェントAのworktree
git worktree add ../DenUni-claude-0-library agent/claude-sonnet-0/library

# エージェントBのworktree（別スラッグ）
git worktree add ../DenUni-codex-0-auth agent/codex-gpt5.5-0/auth
```

**クラウド並列（Remote Agent など）**

クラウドエージェントは独立した環境で動くため、worktreeの代わりにブランチの命名規則で衝突を避ける。起動時にブランチ名を明示的に渡し、終了時にdevelopへのマージPRを作成させる。

**共通ルール**

- `main` への直接pushは禁止。AIのマージ先は常に `develop`
- 同じ提案・設計を複数エージェントが同時に実装しない
- 並列作業の割り当ては人間が行い、Markdownに記録する

## よいAOTP文書の条件

- 目的が最初に分かる
- 現状、判断、未解決事項が分かれている
- 関連文書へのリンクがある
- 読む順番が推測しやすい
- 人間が短時間でレビューできる
- AIが追加質問なしで次の行動を選びやすい
- 古い状態と現在の状態が混ざっていない
- 危険操作、権限、制約が明示されている
- Gitの差分として読みやすい

## 避けるべきこと

- 重要な判断をチャットだけに残す
- 目的と実装手順を混ぜる
- type固有のstatusとTask checkpointを更新しない
- 古い設計と新しい実装を同じ正しさで残す
- 人間だけが分かる省略を書く
- AIだけが読める長大な文脈に依存する
- Markdownに書かれていない暗黙の前提で作業する

## DenUniでの位置づけ

DenUniの `docs/` は、単なる説明書ではなく作業状態そのものである。

提案書、調査結果、設計書、機能仕様、実装メモ、エージェント用スキルは、人間とAIが同じ状態に復帰するための外部記憶として扱う。

AOTPは、この運用に名前を付け、意識的に続けるための概念である。

## DenUniでの課題

DenUniはすでにAOTP的な運用に近い。
ただし、AOTP実行基盤として見ると、まだ足りないものがある。

- **索引が弱い**: 全体状態と読む順番を一目で見る場所がない。
- **台帳がない**: 提案、設計、実装、担当ブランチ、ステータスの対応を一覧できない。
- **精査記録が弱い**: 提案や設計へのレビュー結果が会話だけに残りやすい。
- **検証が弱い**: Markdownのリンク切れ、ステータス不一致、実装対応漏れを機械的に確認できない。

つまり、DenUniの課題は「文書を書くこと」ではなく、文書同士をつなぎ、状態を一覧し、正しさを検証する仕組みがまだ弱いことである。

## Rails on Railでの解釈

ここより上はAOTPの中核概念としてDenUni版をそのまま配置している。この節では、Rails on Rail固有の開発体制と文書構成だけを定める。

### Epicは開発Phase

このプロジェクトでは、Phase -1からPhase 6までの各開発段階をEpicとして扱う。

- ゲーム機能の作業は、原則として関係するPhase Epicへ結びつける。
- Epicは、その段階で何を成立させるか、責任範囲、対象外、完了条件、受入状態を保持する。
- 個別Taskの完了だけでEpic完了とはせず、Epic自身の完了条件で判断する。
- 軽微な修正、開発基盤、複数Phaseにまたがる横断作業は、無理に単一Epicへ所属させなくてよい。
- 主となるPhaseが明確でない横断Taskは、関連Phaseを列挙する。

現在のEpicは[Phase -1 技術プロトタイプ](epics/phase-minus-one.md)である。

### 文書構成

```text
AI.md                     全AIエージェント共通命令の正本
AGENTS.md / CLAUDE.md     ツール別の入口
docs/
  README.md               文書索引
  aotp.md                 AOTP原典とプロジェクト解釈
  workflow.md             Rails on Rail固有の作業手順
  epics/                  Phaseごとの目的と受入条件
  task-index.md           現在のTask一覧
  tasks/                  作業単位と検証結果
  designs/                実装方法と設計判断
  research/               調査結果と出典
  features/               現在実装されている仕様
  impl-notes/             設計との差異と注意
```

### 文書化の目安

| 変更 | 原則として残す文書 |
|---|---|
| 誤字、リンク、意味を変えない整理 | 変更対象のみ |
| 調査のみ | Task + Research。該当する場合はEpic |
| 機能追加、挙動変更 | Task + Feature。重要な判断があればEpic + Design |
| アーキテクチャ、データ形式変更 | Task + Design。必要ならEpic + Research |
| Designと異なる実装 | 上記 + Impl-note |

Taskは、将来の作業者へ目的や判断を引き継ぐ必要がある場合に作る。Designは、複数案の比較、公開インターフェース、データ形式、将来へ影響する判断がある場合に分離する。

### 運用の強化

開発の進行に伴って文書の量が増えることを前提とし、次の状態になったら手動運用から機械検証へ移行する。

- 進行中Taskが常時5件を超える: Task索引を自動生成する。
- 複数エージェントが並行実装する: worktree、担当領域、統合方法を定義する。
- リンク切れや状態不一致が発生する: 文書検証スクリプトを追加する。
- Featureが増える: 実装、テスト、Featureの対応を検査する。
- 人間確認が複雑になる: 変更説明と受入確認のテンプレートを追加する。

Rails on Rail固有の実行手順は[開発ワークフロー](workflow.md)、文書の入口は[ドキュメント索引](README.md)を正本とする。
