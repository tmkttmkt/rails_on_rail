# 開発ワークフロー

## 完了の定義

変更の目的と影響が説明でき、必要な実装と文書が一致し、実行可能な検証結果と未確認事項が記録されている状態を完了とする。

## 作業の流れ

### 1. 現在の状態を読む

`AGENTS.md`または`CLAUDE.md`から`AI.md`へ入り、文書索引、現在のactive Epic、Task一覧、担当Taskの順に読む。現在のGit差分も確認し、他者の未完了変更を自分の作業として扱わない。

### 2. 作業単位を決める

[AOTP運用](aotp.md#taskを必要とする基準)に従い、必要な場合は実装前に`docs/tasks/`へTaskを作成して`docs/task-index.md`へ追加する。対応するEpicが明確なら、そのEpicへ関連づける。旧Phase番号だけから所属を推定しない。

Taskには最低限、次を記載する。

- 目的・背景
- 所属Epic
- 責任範囲
- 対象外
- 完了条件
- 関連文書
- 検証方法

### 3. 必要な調査と設計を行う

外部仕様や技術候補を判断根拠にする場合は`docs/research/`へ分離する。機能実装、構造変更、データ形式変更で重要な選択や将来への影響がある場合は、`docs/designs/`へ実装方法を記録する。

実装方法が局所的で自明な場合はDesignを省略し、必要な判断だけTaskへ簡潔に記録してよい。

### 4. 最小範囲で実装する

Taskの責任範囲を越える変更を混ぜない。新しい必要事項が見つかった場合は、現在Taskへ含める根拠を記録するか、後続Taskへ分離する。

### 5. 検証する

変更に応じて、次を確認する。

- 構文、型検査、単体テスト
- 主要な操作経路
- 保存データや公開インターフェースへの影響
- Markdownリンクと文書内容
- Git差分と意図しない生成物

未実行の確認は未実行と記録する。

### 6. 文書と状態を更新する

実装結果、設計との差、検証結果、残作業をTaskへ記録する。実装済みの挙動は`features/`へ反映し、設計との差異は`impl-notes/`へ記録する。

Taskの状態は次の順で扱う。

```text
ready → in-progress → review → done
                       └→ cancelled
```

- `ready`: 目的と完了条件が定義され、着手可能
- `in-progress`: 作業中
- `review`: 実装側の確認が終わり、人間確認またはレビュー待ち
- `done`: 完了条件と必要な確認を満たした
- `cancelled`: 実施しないと決定し、理由を記録した

### 7. 引き継ぐ

完了時または中断時に、完了したこと、残作業、未確認事項、次に読む文書をTaskへ残す。Task一覧を実態に合わせて更新する。

## Git運用

現在は`main`に加えて`prototype/bekasovo-yard`などの試作ブランチがある。試作内容を`main`へ自動的に取り込まない。

- エージェントは明示的な依頼なしにcommit、merge、pushを行わない。
- 複数作業を並行する場合は、作業ごとにbranchまたはworktreeを分離する。
- ブランチ戦略を導入する場合は、実在する開発体制を確認してからこの文書へ記載する。
- コードと対応文書は同じ変更単位に含める。

## 人間による確認

UI操作、ゲームとしての感触、視認性、バランスなど、機械確認だけでは判断できない項目はTaskに具体的な確認手順を記載する。人間が確認するまでは`review`とし、結果を推測して`done`にしない。
