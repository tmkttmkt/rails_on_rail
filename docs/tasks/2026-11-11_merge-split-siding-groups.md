# Task: 無意味に分かれた留置線群をまとめる

## 目的・背景

2026-11-11のユーザー指摘による。留置線群・検修線群が不必要に細かく分かれていた。森林公園検修区14領域、和光検車区12領域、森林公園駅構内側線6領域という状態で、1線だけの端数領域が複数あった。

原因は、線群の分割を停車範囲（区間）単位で判定していたことである。`partitionStationStopPoints`は並行・横方向の近さ・長手方向の重なりで区間を結合するが、**分岐支障で分断された同一線路の区間同士は長手方向に重ならない**ため結合されない。結果として1本の線路が複数の領域へ分かれ、残りの短い区間が1線だけの領域として余った。

実データで確認した例。森林公園検修区では線路225が第2・第3・第12線群の3領域へ、線路183・223・224・227がそれぞれ2領域へ分かれていた。第10〜第13線群はいずれも1線のみで、すべて他領域にある線路の端数だった。和光検車区では線路69が第4・第5・第6線群の3領域へ分かれていた。

## 責任範囲

- 同じ線路の停車範囲が必ず同じ領域へ入るようにする。
- 領域あたりの上限を停車区間数ではなく線路数で数える。
- 東上線の領域マップと短編成試験セーブを再生成する。

## 対象外

- `partitionStationStopPoints`自体の並行判定の変更。既存の呼び出し元（ベカソヴォ分割）とテストは変えない。
（当初は対象外としていた`maximumTracksPerArea`の扱いを、2026-11-11の追加指摘で範囲へ含めた。下記を参照。）
- 領域の用途・役割の再判定、グループ構成の変更。
- 川越市の手書き区分。距離で区切った待機線と引上げ線、残余の分岐区間は意図的な区分として維持する。

## 完了条件

- [x] 1本の線路が複数の領域へ分かれない（川越市の意図的な距離区分を除く）。
- [x] 幾何的に一つの線群が、線路の本数の上限で複数の領域へ分かれない。
- [x] 他領域の線路の端数だけでできた1線領域が残らない。
- [x] 停車範囲を欠落・重複させずに配分する。
- [x] 型検査、全テスト、ビルド、領域・試験の再生成が成功する。

## 方針・判断

- 幾何の判定結果は保つ。区間単位の並行判定を行ったあと、**線路を共有する線群同士を統合する**。代表区間（最長区間など）だけで判定し直す方法も試したが、代表の選び方によって線群の所属が変わり、元の隣接情報を失うため採用しなかった。
- 処理は`src/simulation/stationPartition.ts`へ`partitionStationStopPointsByTrack`として置き、テストできるようにした。生成スクリプト内に残さない。既存の`partitionStationStopPoints`は変更しない。
- 上限の分割は線路単位で行う。線路を領域の境目で割れば、統合した意味がなくなる。
- 生成時に、元の停車範囲を過不足なく重複なく配分したことと、同じ線路が複数の線群へ分かれていないことを検査する。

## 検証方法

- 単体テストで、分断された同一線路の区間が1線群へまとまること、線路を共有しない線群が結合されないこと、3領域以上に跨る場合も畳めることを確認する。
- 再生成した領域マップで、同一線路が複数領域へ分かれていないことを数える。
- 型検査、全テスト、ビルド、`generate:tojo-areas`・`generate:tojo-trial`。

## 作業結果

`partitionStationStopPointsByTrack`を[stationPartition.ts](../../src/simulation/stationPartition.ts)へ追加した。既存の区間単位の分割を実行し、線路を共有する線群が無くなるまで統合する。既存の`partitionStationStopPoints`とその呼び出し元・テストは変更していない。

[generate-tojo-station-areas.ts](../../scripts/generate-tojo-station-areas.ts)を新関数へ切り替え、上限の分割を線路単位にした。配分後に、停車範囲の件数とIDの重複、同じ線路が複数線群へ分かれていないことを検査して中止できるようにした。



|グループ|当初|同一線路の統合後|本数上限の撤去後|
|---|---:|---:|---:|
|森林公園検修区|14|10|**7**|
|和光検車区（東京メトロ・参考）|12|6|**4**|
|森林公園駅構内側線|6|3|3|
|小川町留置線|4|3|3|
|成増構内側線|4|3|3|
|下板橋留置線|3|3|**2**|

合計は54領域から41領域を経て35領域になった。

1線だけの端数領域（森林公園検修区の第10〜第13線群、和光検車区の第5・第6・第9・第10線群など）は解消した。残る1線領域は幾何的に独立した単独側線であり、端数ではない。

統合により停止可能長の見え方も変わった。下板橋第1線群は最長265.8 m、森林公園検修区第6線群は437.1 m、和光検車区第5線群は316.4 mとなり、従来は同じ線路が分かれていたため短く見えていた。

### 追加指摘：本数の上限による分割（2026-11-11）

「下板橋は？」という指摘を受けて、幾何的な線群と実際の領域を照合した。結果は次のとおり。

|施設|幾何的な線群|上限適用後の領域|上限による分割|
|---|---:|---:|---|
|下板橋留置線|1群（8線）|2|あり。6線＋2線へ分断|
|森林公園検修区|6群|10|あり。14線群と8線群を分断|
|和光検車区（参考）|3群|6|あり。16線群を分断|
|森林公園駅構内側線|2群|2|なし|
|成増構内側線|2群（各1線）|2|なし。幾何的に独立|
|小川町留置線|2群（各1線）|2|なし。幾何的に独立|

下板橋は8線が並行し長手方向も重なる一つの線群であり、6線＋2線の分割は`maximumTracksPerArea: 6`だけが原因だった。分割位置はx座標順の機械的な区切りで、二つの領域に区別がない。

そこで本数による分割を撤去し、領域を幾何的な線群とそのまま一致させた。`maximumTracksPerArea`は設定と生成スクリプトから削除した。領域数は41から35へ減った。下板橋留置線は8線1領域となり、線群が一つなので名称は「第N線群」を付けず「下板橋留置線」になる。

成増と小川町の1線領域は幾何的に独立した単独側線であり、上限とは無関係のため従来どおり分かれている。

## 検証結果

- `npx tsc` 成功。
- 本数上限の撤去後も `npx tsc`・`npx vitest run` 35ファイル285テスト・ビルド成功。`generate:tojo-areas` は12グループ・35領域、未所属区間0・他グループ所有0。`generate:tojo-trial` は33駅・64区間一致。
- `npx vitest run` 35ファイル285テスト成功。[stationPartition.test.ts](../../tests/stationPartition.test.ts)へ4件追加した。分断された同一線路を1線群へまとめること（区間単位では2線群に分かれることも同時に検査）、線路を共有しない線群は結合しないこと、3線群以上に跨る場合も1つへ畳むこと、空集合と不正設定、入力を破壊しないことを検査する。
- ビルド成功（既存の500 kB超警告あり）。
- `npm run generate:tojo-areas` 成功。12グループ・41領域、全12グループで未所属区間0・他グループ所有0。
- `npm run generate:tojo-trial` 成功。33駅・上下64区間の有向探索一致。
- 再生成した領域マップで、同一線路が複数領域へ分かれているのは川越市の2件だけである。線路144を距離310 mで待機線と引上げ線に区切った意図的な区分と、線路292の留置可能範囲外を残余の分岐区間が持つ構造的なものである。

## 未確認事項・残作業

- 本数の上限を撤去した結果、森林公園検修区に14線、和光検車区に16線の領域ができた。並行して長手方向が重なる一つの線群だが、施設タブの領域一覧と詳細表示でこの行数が扱いやすいかは人間確認待ちである。扱いにくければ幾何の判定条件（横方向16 m・重なり55%）を見直す方が、本数で割るより筋がよい。
- 検修区・検車区の内部を建物機能や検査種別で分けることは引き続き未確認である。現在の区分は幾何による線群であり、現地の実区分ではない。
- 「志木留置・引上げ線」は元施設区分のまま留置と引上げを1領域に含む。今回の変更対象外である。
- 領域名の「第N線群」の番号は再生成で振り直される。既存セーブで領域名を参照していた場合は一致しない。
- 画面での見た目は人間確認待ち。領域数が減ったことで番号丸と色面の重なりがどう見えるかは未確認である。

## 引き継ぎ

人間確認は`/?map=tojo-areas`の施設タブで、森林公園検修区と和光検車区を開き、線群の分かれ方と各領域の線路一覧・停止可能長を確認する。右パネルの詳細表示で線路と長さを見られる。

再生成の順序は`generate:tojo-areas` → `generate:tojo-trial`。生成物はODbL継承のため`.gitignore`対象で、正本は設定YAMLと生成スクリプトである。
