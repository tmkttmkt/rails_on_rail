# Rails on Rail データ定義

このディレクトリは、ゲーム内で使用する鉄道規格・設備・技術データの正本である。

現在は鉄路データから定義する。車両、年代、技術ツリーは鉄路の構造が安定してから追加する。

## 形式

編集用の原本にはYAMLを採用する。

理由:

- 人間とAIの双方が読み書きしやすい
- JSONより差分が小さく、レビューしやすい
- 単位、出典、未確定事項をコメントで残せる
- 同種のカタログを簡潔に記述できる

実行時にJSONが必要になった場合は、検証済みYAMLから生成する。YAMLとJSONを両方手編集して正本を二重化しない。

### YAML運用制限

YAMLの柔軟性による解釈差を防ぐため、次を守る。

- YAML 1.2として解釈する
- インデントは半角スペース2個
- タブを使用しない
- アンカー、エイリアス、マージキーを使用しない
- カスタムタグを使用しない
- 日付は`YYYY-MM-DD`形式の文字列として引用する
- `yes`、`no`、`on`、`off`など型が曖昧な文字列は引用する
- 数値へ単位を含めず、キー名で単位を示す
- キーはTypeScriptから直接扱いやすい英語camelCaseにする
- 列挙値と永続的な機械識別子は英小文字のkebab-caseにする
- 名称、説明、注記、YAMLコメントは日本語で記述する
- 表示名、説明、出典と機械判定用の値を分離する

例:

```yaml
id: dc-1500v-overhead # 永続的な機械識別子
name: 直流1500V架空電車線方式
voltageV: 1500 # 電圧。単位はV
availableFrom: "1920-01-01"
```

## データ境界

```text
data/
  sources.yaml         出典資料の共通カタログ
  track/              鉄路と、鉄路に沿って設置される電化設備
  legal/              法制度、違反、特例認可、取締方針
  vehicles/           車両設計、連結器、ブレーキ方式
  power-facilities/   変電所、き電区分、電力供給設備
  signaling/          信号、閉塞、列車検知、連動
  train-protection/   ATS、ATCなど地上・車上保安装置
  schemas/            YAMLを検証するJSON Schema
```

### `track/`

列車を物理的に支持・案内する設備と、線路に沿って設置される電化設備を扱う。

- 軌間
- レール
- 軌道支持方式（締結、枕木・支持構造、道床）
- 路盤
- 軸重制限
- 線形制約
- 橋梁・トンネルとの適合条件
- 架線・第三軌条などの集電設備
- 電圧、電流方式、周波数
- 地図上の線路セグメントが持つ法的状態と敷設形態

線路の法制度と、路面・専用線路敷などの物理的な敷設形態は分離して扱う。詳しいセグメント境界の原則は[鉄路データ](track/README.md#線路セグメント)を参照する。

### `power-facilities/`

線路区間の属性ではなく、地図上に独立して存在する電力設備を扱う。

- 変電所
- き電区分所
- き電区間
- 供給容量

### `signaling/`

列車間隔と進路を管理する運行保安設備を扱う。

- 信号方式
- 閉塞方式と閉塞区間
- 軌道回路などの列車検知方式
- 連動装置

### `train-protection/`

信号確認や速度制限を自動的に補完する保安装置を扱う。

- ATS
- ATC
- 地上装置と車上装置の互換性
- 制動介入方式

### `legal/`

車両、軌道、運行、事業者に共通する法的状態を扱う。

- 地域・時代ごとの法制度
- 違反行為と継続的な違反状態
- 正式な特例認可制度
- 発覚、黙認、警告、処分を決める取締方針

物理的に運行可能かという判定と、法的に運行可能かという判定を混在させない。詳細は[法的状態データ](legal/README.md)を参照する。

### `vehicles/`

製造会社が持つ車両設計を機関車、動力車、客車、貨車へ分けて定義する。連結器と貫通ブレーキ方式もこの領域で扱う。プレイヤー会社の形式と車両個体は保存データへ置く。詳細は[車両データ](vehicles/README.md)を参照する。

## 共通フィールド

すべてのカタログ項目は原則として次を持つ。

| キー | 必須 | 意味 |
|---|:---:|---|
| `id` | ✓ | 永続的な機械識別子。値は英小文字のkebab-case |
| `name` | ✓ | 日本語表示名 |
| `description` |  | 人間向けの説明 |
| `status` | ✓ | `draft`、`researched`、`verified`、`deprecated` |
| `introducedYear` |  | 実用化・利用開始年。ゲームでの解禁年とは分離する |
| `sources` |  | 根拠資料のID一覧 |
| `notes` |  | モデル化上の注意 |

`introducedYear`は歴史上の事実であり、ゲームバランス上の解禁時期は将来の技術・年代データで定義する。

## 数値と単位

内部基準単位をキー名へ明示する。

| 量 | キーの接尾辞 | 基準単位 |
|---|---|---|
| 長さ | `Mm`、`M` | mmまたはm |
| 質量 | `Kg`、`T` | kgまたはメートルトン（t） |
| 速度 | `Kmh` | km/h |
| 電圧 | `V` | V |
| 周波数 | `Hz` | Hz |
| 線密度 | `KgPerM` | kg/m |

同じ量へ複数単位を混在させない。表示時の単位変換はUI側で行う。

`T`はメートルトンを表す。キー全体で意味を判断できるため他の単位とは衝突しないが、テスラなど別の量へ`T`を流用しない。

## 状態

- `draft`: 仮入力で、資料確認前または構造検討中
- `researched`: 資料を確認したが、値または解釈の検証が未完了
- `verified`: 出典、値、解釈を検証済み
- `deprecated`: 廃止済み。既存参照のために保持

`researched`は「資料に記載された事実」と「資料を基にしたゲーム用推定」を区別して記録する。推定値が含まれるだけでは`verified`にしない。

## 出典

複数項目から参照する資料は[`sources.yaml`](sources.yaml)へ一度だけ登録する。各データの`sources`には、その永続IDを記録する。

## IDと参照

- IDはファイルを移動しても変更しない
- 表示名をIDとして使用しない
- 他カタログへの参照は`<target>Id`または`<target>Ids`とする
- 参照先が存在しないデータを`verified`にしない
- 削除ではなく`deprecated`で廃止を表現し、後継IDを記録する

## プリセットと構成要素

軌間、レール、電化方式などの構成要素を別々のカタログとして定義する。これらを組み合わせた建設用プリセットは`track/standards.yaml`で参照する。

巨大な「線路レベル」へすべてを埋め込まない。構成要素を個別に交換・更新できることを優先する。

## 検証方針

- YAML構文を検証する
- JSON Schemaで必須フィールド、型、範囲、列挙値を検証する
- IDの一意性と参照整合性を検証する
- `verified`データには少なくとも1つの出典を要求する
- コードで利用する前に検証済みJSONへ変換できるようにする

現段階のカタログ項目は構造検討用の`draft`であり、史実・工学値の検証完了を意味しない。
